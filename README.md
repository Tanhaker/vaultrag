# VaultRAG: Secure Multi-Modal RAG with Access Control

[![CI](https://github.com/Tanhaker/vaultrag/actions/workflows/ci.yml/badge.svg)](https://github.com/Tanhaker/vaultrag/actions/workflows/ci.yml)

Code Carnival 2026, Atmiya University · PS-01 · Team **FriendlyFire** (TXJ8): Bhakti Kareliya (team leader), Tanmay Gajjar.

**Live demo:** https://vaultrag-nine.vercel.app (fictional data; demo accounts below)

VaultRAG answers natural-language questions over PDFs, scanned pages, photographed notices and
database records. Access control is enforced **inside Postgres, on the same statement that runs the
vector search**, so application code cannot leak a document the caller isn't cleared for: the
database never returns it. Every sentence of every answer is cited to an exact page region, image
region, table row or live SQL result, a verifier removes sentences the sources don't support, and
every answer comes with a signed receipt anyone can re-verify later.

## What it does

**Multi-modal ingestion.** PDFs (text blocks with page regions, ruled tables, running headers removed),
scanned pages and photos (Gemini vision OCR with region boxes and a caption, Tesseract offline),
and database rows turned into record cards that keep their row's ACL. Heading-aware chunks,
sha256 dedupe, prompt-injection scan, 768-d embeddings, tripwire canaries registered automatically.

**Retrieval-layer authorisation.** HNSW (iterative scan) + BM25 under Postgres RLS, fused with RRF and
re-ranked. `acl_check()` runs inside the scan of `chunks`; the Trust Center shows it in a live
EXPLAIN ANALYZE as any identity.

**Grounded answers.** Gemini (JSON-schema citations) or a verbatim composer; a verifier checks
citations, figures and entailment; uniform refusal; Text-to-SQL for aggregates under the same RLS.

**Ten layers between a question and a leak**

| # | Layer | Enforced in |
|---|---|---|
| 1 | Verified identity: HS256 JWT, identity never from the request body | API |
| 2 | HMAC-signed DB context, expiry, **account kill switch** inside `app_ctx()` | Postgres |
| 3 | Row-level security on every table, inside the vector and keyword scans | Postgres |
| 4 | Column masking (salaries, student phones/emails) and **k-anonymous pay statistics** (k = 5) | Postgres |
| 5 | Text-to-SQL firewall: one validated SELECT over whitelisted views, read-only, 5 s timeout | API + Postgres |
| 6 | Prompt-injection quarantine; sources passed as data | API |
| 7 | Citation verifier: verbatim quote, figures in source, LLM entailment | API |
| 8 | **Egress DLP**: canaries checked against RLS before an answer leaves; phone/ID redaction | API + Postgres |
| 9 | **Signed answer receipts** (HMAC over question, answer and source hashes) | API |
| 10 | **Hash-chained audit log** + probing alerts | Postgres |

**Beyond the problem statement**

- *Aggregate-only access with k-anonymity.* Heads of department see their department's average pay
  for planning, never an individual salary; one fixed grouping blocks differencing attacks.
- *Timing side channel, measured.* Forbidden rows are removed inside the scan, so refusing a
  forbidden document takes as long as refusing a missing one (`bench/timing_sidechannel.py`).
- *Verifiable receipts.* Any answer can be checked later: signature, answer text, and whether each
  source still says the same (re-read under the checker's own RLS).
- *Tamper-evident audit.* Every audit row hashes the previous one; `audit_chain_verify()` re-walks it.
- *Probing detection + kill switch.* Refusals, guessed citation links and DLP blocks raise an alert;
  locking an account takes effect inside the database, even for a still-valid token.
- *Governance tools.* Live access matrix from `acl_check()`, and a what-if ACL preview that names who
  gains or loses access before you save.
- *Quota-aware AI.* Model chain across free-tier quotas, a daily budget and per-user fair use, an
  RLS-scoped Postgres answer cache shared by all serverless instances, and a verbatim mode that
  answers with no model at all.
- *Conversations.* Follow-up questions are rewritten deterministically ("what about MECH?") and
  access is checked again on every turn.

## Quick start (local)

```bash
cp .env.example .env                     # replace every change-me value; add GEMINI_API_KEY for LLM mode
docker compose up -d --build             # Postgres 16 + pgvector 0.8, FastAPI on :8000 (runs migrations)
docker compose exec api python -m app.cli seed          # synthetic students, staff, fees, demo users
docker compose exec api python -m app.cli ingest-demo   # generate + ingest PDFs, scans, photos, record cards
docker compose exec api pytest -q                       # RLS matrix, trust layer, red-team suite, units
cd frontend && npm install && npm run dev               # http://localhost:5173 (proxies /api → :8000)
```

Evaluation and benchmarks (from `backend/`): `python -m bench.grounding_eval`,
`python -m bench.timing_sidechannel`, `python -m bench.recall_benchmark`, then
`python -m bench.export_measured` to refresh the Trust Center's offline numbers.

Without a Gemini key the pipeline still runs end to end: deterministic hash embeddings, Tesseract
OCR and the verbatim composer (this is what CI runs). With a key it uses `gemini-embedding-001`
(768-d), Gemini generation with JSON-schema citations, an LLM entailment verifier and vision OCR.
Generation walks a model chain (`LLM_MODEL`, then `LLM_FALLBACK_MODELS`); a 429 parks that model
until Google's `retryDelay` and the next one answers. Over the daily budget
(`LLM_DAILY_BUDGET`) or the per-user fair-use limit, answers are quoted verbatim instead of failing.

## Pipeline

```
upload ─► sha256 dedupe ─► PDF text blocks + ruled tables (PyMuPDF, pdfplumber)
                         └► scans / photos: Gemini vision or Tesseract OCR (+ caption)
        ─► heading-aware chunks with page + bbox ─► injection scan ─► embeddings ─► Postgres
           (each chunk inherits its document's ACL through a trigger; canaries registered)

question ─► JWT ─► preflight (one RLS round trip: data version, usage, Postgres answer cache)
          ─► rate limit ─► follow-up rewrite ─► quota guard
          ├─ aggregate? ─► Text-to-SQL (template first) ─► sqlglot validation ─► run under RLS
          │                + masking / k-anonymous views ─► cited, figure-checked summary
          └─ HNSW (iterative scan) + BM25, both under RLS ─► RRF ─► feature rerank
             ─► quarantine injected chunks ─► Gemini answer (JSON, cited) or verbatim composer
             ─► verifier: citation validity + figures-in-source + verbatim / LLM entailment
          ─► egress DLP ─► uniform refusal if nothing survives ─► signed receipt
          ─► hash-chained audit row + RLS-scoped cache write (one transaction)
```

## How authorisation works

```
JWT (verified) ──► UserCtx ──► BEGIN READ ONLY
                               set_config('app.ctx',     {uid,tid,roles,depts,clr,exp}, true)
                               set_config('app.ctx_sig', HMAC-SHA256(ctx, secret),      true)
                               SELECT … FROM chunks ORDER BY embedding <=> $q LIMIT k
                                        └── RLS policy: acl_check((SELECT app_ctx()), …)
                               COMMIT  (context gone with the transaction)
```

1. **Least-privilege roles.** User queries run as `rag_reader`: `NOBYPASSRLS`, SELECT only, no grant
   on base `employees`, `users`, `app_secrets`, or student contact columns. Ingestion and admin ACL
   changes use `rag_writer`.
2. **Signed context.** SQL running as `rag_reader` can call `set_config` (including LLM-written SQL),
   so `app_ctx()` trusts the context only if its HMAC verifies against a key the reader cannot read,
   it has not expired, and the account is not locked. Otherwise it is `NULL` and every policy fails closed.
3. **RLS on every table**, forced. Documents and chunks: same tenant AND (explicit user grant OR
   (clearance ≥ classification AND role allowed AND department in scope)). Students, fees, audit log,
   image blobs, canaries and the answer cache have their own policies.
4. **ACL inheritance and instant revocation** through triggers on `chunks` and `documents`; a
   per-tenant data version (bumped by triggers) keys every cache, so revocation reaches every instance.
5. **Column masking and aggregate-only views**: `employees_secure`, `students_secure`, `salary_stats`.
6. **Transaction-local, read-only sessions**: safe behind Neon's PgBouncer in transaction mode.

## Deployment (Vercel + Neon)

`vercel.json` builds the frontend to static files, serves `api/index.py` (FastAPI, mounted at
`/api`) as a Python function, and sets security headers (CSP, HSTS, frame denial). The database is
Neon Postgres with pgvector; the function connects per request through Neon's pooler. Migrations,
seeding and ingestion run from a workstation with `DATABASE_URL` pointing at Neon's direct
(unpooled) endpoint. `.env.neon` (gitignored) holds that owner URL plus the same secrets the Vercel
project has:

```bash
docker exec --env-file .env.neon vaultrag-api-1 python -m app.cli migrate
docker exec --env-file .env.neon vaultrag-api-1 python -m app.cli seed
docker exec -e EMBED_WAIT_SECONDS=900 --env-file .env.neon vaultrag-api-1 python -m app.cli ingest-demo
docker exec --env-file .env.neon vaultrag-api-1 python -m bench.live_check https://vaultrag-nine.vercel.app
docker exec --env-file .env.neon vaultrag-api-1 python -m app.cli warm-cache   # demo questions, cached in Postgres
```

Vercel needs `DATABASE_URL` (added by the Neon integration), `DB_READER_PASSWORD`,
`DB_WRITER_PASSWORD`, `JWT_SECRET`, `CTX_HMAC_SECRET` (the same values the migration used, since
`app_ctx()` verifies the HMAC with the key stored in Postgres), `GEMINI_API_KEY`, `DEMO_MODE`,
`LLM_MODEL` and `MAX_UPLOAD_MB=4` (function request bodies are capped at 4.5 MB).

Managed-Postgres notes:
- Neon's owner role (`neondb_owner`) is not a superuser but has `BYPASSRLS`. Requests never use it:
  every query runs as `rag_reader`/`rag_writer`, which have neither. The masking views do their own
  row scoping, so they are correct whoever owns them; the owner gets explicit policies where its
  own functions read rows (006, 008).
- On a corpus this small the optimiser may choose an exact sequential scan over HNSW; the RLS filter
  runs inside either. The EXPLAIN view shows the planner's choice and the forced HNSW plan.
